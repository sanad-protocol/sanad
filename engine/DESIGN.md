# Sanad engine 0.2: design

This document describes the Sanad engine: a small program that runs assessments end to end and produces Sanad credentials that a verifier can check (hashes, signatures, log proofs) and evaluate under its own policy. It implements algorithm `sanad-0.1` of SANAD-SPEC-0.1 with three differences from the v0.1 reference that are open spec decisions (section 14, item 32). Package version 0.2.0; algorithm string `sanad-0.1`.

## 1. Scope

The engine does:

- hold **assessment templates** (skill, levels, rubric, evidence plan, attestor requirements, recommended verifier policy, live-sitting flag);
- run **one assessment**: create it, invite attestors by DID, accept **blind commits**, then **reveals**, enforce deadlines, record missing and late reveals;
- build the **evidence chain** and seal a **credential** with the core library (`reference/`), sign it with the issuer key, and append hashes to a **transparency log** (Merkle tree with inclusion and consistency proofs, signed checkpoints);
- **verify** a credential: issuer proof, bundle hash, attestor signatures, log inclusion, then the recognition function under the verifier's own policy;
- offer the same through a library, an HTTP API (`node:http`), a CLI and a small demonstration page.

The engine does not: vet attestors (spec section 9: nobody vets them for the protocol); run a live room, video or proctoring; take payments; fetch DID documents over the network; publish skill cards or run an index; implement selective disclosure (SD-JWT); anchor checkpoints in OpenTimestamps; rank people. It is not accreditation and claims nothing about the honesty of a sitting: a chain says what was observed.

Runtime dependencies: none. Node 22 or later (`node:crypto` Ed25519, `node:http`, `node:fs`; `node:sqlite` only if present). `esbuild` and `vitest` are development tools of the repository, used to build the single-file bundles and to run tests.

## 3. Data formats

Everything is JSON, hashed as SHA-256 over the canonical form of the core library (RFC 8785: UTF-16 key order, ECMAScript string escaping and **ECMAScript `Number` formatting for every number**). Signed statements are built from strings, booleans, small integers and arrays; the attestor statistics (`agreement`) and the policy fractions are non-integer numbers inside the issuer-signed credential and are serialized with the ECMAScript shortest round-trip form, which a second implementation must reproduce (the Python cross-check does). Numbers beyond 2^53, non-finite numbers and lone surrogates are refused at the HTTP boundary and in the library (`ijson.mjs`).

**Identifiers.** Attestor and issuer ids are DIDs. `did:key` (Ed25519, multicodec `0xed01`, base58btc, prefix `z`) works with no registry; it cannot rotate. Any other DID (for example `did:web:...`) must be registered with the engine as a **DID document history** (section 5). The verification method id (`kid`) is `<did>#<fragment>`; for `did:key` the fragment is the multibase key.

**Detached JWS.** Every signature is a JWS (RFC 7515) in compact form with a detached payload: `BASE64URL(header) + ".." + BASE64URL(signature)`. The header is the canonical JSON of `{ "alg": "EdDSA", "kid": <kid>, "typ": <type> }`. The signing input is `BASE64URL(header) + "." + BASE64URL(UTF-8(canonical(payload)))`. The `typ` separates statement kinds, so a signature made for one kind is never accepted for another:

| `typ` | Signed by | Payload |
|---|---|---|
| `sanad-commit+jws` | attestor | `{ type: "sanad-commit", assessment, attestationId, attestor, evidence, role, commit, templateHash }` |
| `sanad-attestation+jws` | attestor | the attestation without `prev`, `hash`, `signature`: `{ id, attestor, evidence, level, role, conflictDeclared, date, commit, nonce }` |
| `sanad-credential+jws` | issuer | the credential document without `proof` |
| `sanad-checkpoint+jws` | log operator | `{ logId, size, rootHash, timestamp }` |
| `sanad-did-update+jws` | a key valid in the previous DID document version | the new version |

A verifier refuses a JWS whose `alg` is not `EdDSA`, whose `typ` differs from the expected one, whose `kid` does not belong to the expected signer (the attestor of the attestation, the issuer of the credential), whose key was not valid on the statement's date, or whose header has any other member.

**Commit.** As in the reference code and the vectors: `commit = SHA-256(canonical({ attestor, evidence, level, nonce }))`. The engine creates a 128-bit random nonce (22 base64url characters) and refuses shorter nonces on new commits (the level space is 0..5, so the nonce is what hides the mark).

**Attestation.** The reference shape (`id, attestor, evidence, level, role, conflictDeclared, date, commit, nonce, prev, hash, signature`). `signature` holds the attestor's `sanad-attestation+jws`. `prev` and `hash` are added by the issuer at sealing (chain in id order, `GENESIS` first), so an attestor can sign before the order is known. A sealed attestation with any other member is refused by the engine verifier (unhashed members would be malleable).

**Evidence.** The reference shape (`id, kind, date, summary, body, hash`, `hash = SHA-256(canonical(body))`). Because the reference hash covers the body only, the engine copies `kind` and `date` into the body (`body.kind`, `body.date`) and its verifier requires them to match; the bundle hash covers the whole evidence objects.

**Bundle.** The core credential object `{ skill, claimedLevel, subject, evidence, attestations, attestors }`. `bundleHash = SHA-256(canonical({ alg: "sanad-0.1", skill, claimedLevel, subject, evidence, attestations }))` with evidence and attestations sorted by id and complete (including `hash` and `signature`). `attestors` (statistics) is outside the bundle hash because it is a verifier input that a verifier may replace with statistics it pins itself; it is inside the issuer's signature.

**Credential document.** Shaped after W3C VC 2.0; it is not processed as JSON-LD and is not claimed to validate against Open Badges 3.0:

```
{ "@context": ["https://www.w3.org/ns/credentials/v2"], "type": ["VerifiableCredential", "SanadCredential"],
  "id": "urn:uuid:...", "issuer": "<did>", "validFrom": "<ISO date-time>",
  "credentialSubject": { "id": "<pseudonymous subject>", "skill": "<id>", "claimedLevel": n },
  "evidence": [{ "type": ["Evidence", "SanadBundle"], "id": "urn:sanad:bundle:<bundleHash>", "bundleHash": "...", "alg": "sanad-0.1" }],
  "sanad": { "bundle": {...}, "template": { "id", "hash" }, "assessment": "<id>",
             "process": { "invited": n, "committed": n, "revealed": n, "missing": [ids], "late": [ids], "notCommitted": [ids], "removed"?: [ids], "shortfall"?: [text] },
             "policy": { recommended policy of the template, with id },
             "log": { "logId", "entries": [{ "index", "leaf" }], "checkpoint": {...}, "proofs": [...] } },
  "proof": { "type": "SanadDetachedJws", "verificationMethod": "<kid>", "created": "<ISO date-time>", "jws": "..." } }
```

## 4. One assessment, step by step

1. **Template.** The operator registers a template; the engine validates it and pins `templateHash`.
2. **Create.** `createAssessment({ templateId, subject, claimedLevel, evidence, commitBy, revealBy })`. Evidence items follow the template's evidence plan; ids are `<assessmentId>.E<n>`. The subject id is pseudonymous (`urn:uuid:` or another URN); names never enter the engine.
3. **Invite.** `invite({ assessment, attestor, role, evidence })` assigns an attestation id `<assessmentId>.a<nn>`. Refused: an attestor already invited on the same evidence (`duplicate_attestor`), the assessment's `subjectDid` (when given) as attestor (`subject_as_attestor`), a role the template does not allow, more attestors than the template's maximum, a DID the resolver cannot resolve.
4. **Commit (blind).** The attestor computes the commit from its level and a fresh nonce, signs a `sanad-commit+jws`, and sends `{ attestationId, payload, jws }`. Accepted only from the invited attestor, once (`already_committed`, even for an identical commit), before `commitBy` (`commit_closed`). The commit is appended to the log (leaf kind `commit`).
5. **Reveal.** Opens when the roster is complete and every invited attestor has committed, or when `commitBy` has passed (`reveal_not_open` before). The roster is complete when every evidence item of a kind other than `auto` has at least `attestors.min` invited attestors, or when the operator has closed the invitations (`closeInvitations`): without this rule the first invitee's commit would open the reveal phase before the second was invited. Once the phase has opened it never closes (a commit is refused once any reveal exists, and the engine clock never runs backwards). The attestor sends the attestation statement and its `sanad-attestation+jws`. Checks: signature and key validity on `date`; statement fields equal the invitation; `commit` equals the stored commit; `commitOf(statement)` equals the commit (`commit_mismatch`); `level` an integer 0..5 allowed by the template; `date` not before the evidence date and not after the reveal day. After `revealBy` the reveal is refused and recorded as `late`.
6. **Finalize.** Allowed when every commit is revealed or `revealBy` has passed. Commits without a reveal are recorded as `missing` (log leaf kind `missing-reveal`); they produce no attestation. Attestor statistics are computed from earlier finalized assessments (section 7). Before sealing, the template minimum is enforced: every evidence item of a kind other than `auto` needs at least `attestors.min` distinct revealed attestors, and a live-sitting template needs revealed marks on sitting evidence; otherwise `below_template_minimum`, unless the operator passes `allowShortfall`, which adds `process.shortfall` (a list of the unmet requirements) to the credential. The engine then seals evidence and attestations (chain and hashes per the core), computes `bundleHash`, appends each attestation hash and the bundle hash to the log once (a retry after a crash finds the existing leaves), signs the credential and stores it. The credential id is derived from the assessment id and the bundle hash, so that a retry overwrites instead of duplicating.
7. **Verify.** Anyone runs `verifyCredential(doc, opts)` with the verifier's own `policy` (all seven fields) and evaluation day, and the issuer and log key it pins: issuer proof, bundle hash, evidence `kind`/`date` consistency, closed member sets, attestor signatures (passed to the core as a signature check, so a failing signature drops that attestation under R1 with its reason), log inclusion proofs against the embedded checkpoint, then `recognise` and `infer` with the verifier's policy (the template's policy is only a recommendation, used only if the verifier passes `useRecommendedPolicy`, and then labelled). Further checks: attestation and evidence ids belong to the credential's assessment; the issuer and log key are pinned (`ok` is false otherwise unless `allowUnpinned`); `did:web` keys are pinned or the histories supplied by the verifier (an embedded history is only the issuer's claim); issuer-supplied statistics used for a threshold fail unless the verifier supplies its own (`attestorStats`) or accepts them knowingly; a supplied template is checked for hash, roles and evidence kinds. The report lists every check, the full explanation, `basis` (whose policy and day) and the experimental-software `notice`.

## 5. Keys

Ed25519 throughout (RFC 8032, `node:crypto`; WebCrypto `Ed25519` in the demonstration page). **Attestors hold their private keys.** The engine, its HTTP server and its library entry never receive, store or generate an attestor's private key; they receive signed statements only. The issuer key and the log key belong to the operator who runs the engine (`sanad-engine init` writes them to files with mode 0600). `demo-keys.mjs` is a separate helper for scripted demonstrations and tests.

Rotation and revocation: a DID document history is a list of versions `{ version, validFrom, keys: [{ id, publicKeyMultibase }], revoked: [{ id, from }] }`; version 1 is registered by the operator (trust on first registration); every later version must carry a `sanad-did-update+jws` by a key that is valid in the previous version. A key verifies a statement dated D if it is listed in the version in force on D and is not revoked from a day on or before D. `did:key` has no rotation; a lost or compromised `did:key` is replaced by a new identity.

## 6. Storage

Interface (synchronous, single process): `get(collection, id)`, `put(collection, id, value)`, `list(collection)` (sorted by id), `append(stream, value) -> index`, `read(stream, from, to)`, `size(stream)`, `close()`. Collections: `templates`, `assessments`, `dids`, `credentials`. Streams: `log`, `events`. Adapters: `memory`; `file` (one JSON file per record written through a temporary file and rename; streams as JSON lines appended with `fsync`; ids are checked against `^[A-Za-z0-9._:-]{1,200}$` so no path can escape the directory); `sqlite` (two tables, optional table prefix, accepts an existing `DatabaseSync`, so a host service can keep the engine in its own database). Private keys are never put in a store.

## 7. Transparency log and attestor statistics

The log is an RFC 9162 Merkle tree (leaf hash `SHA-256(0x00 || leaf)`, node hash `SHA-256(0x01 || left || right)`). A leaf is the UTF-8 canonical JSON `{ kind, ref, ts }` where `kind` is `commit`, `attestation`, `missing-reveal` or `bundle`, `ref` a SHA-256 hex and `ts` an ISO date-time: hashes only, no names or content. Each stored entry also carries `prev`, the hash of the previous entry, so a damaged file is detected locally. The log offers signed checkpoints, inclusion proofs and consistency proofs with their verification functions.

**The statistics are issuer-supplied and are not recomputable from the log.** The log holds hashes only (no levels, no attestor identities), so a verifier cannot rebuild `sittings` or `agreement` from it, although the specification says so. Treat them as the operator's statement. A verifier that uses them for a threshold either supplies its own statistics (`attestorStats`), restricts attestors (`allowedAttestors`), or accepts the issuer's explicitly (`allowIssuerStatistics`, which adds a warning). Making them verifiable needs a format decision (`docs/SPEC-DECISIONS-NEEDED.md`, decision 4). Attestor statistics (spec 3.4): `sittings` is the number of finalized assessments in which the attestor revealed a mark on `sitting` evidence; `agreement` is the share of the attestor's marks that lie within one level of the lower median of the other attestors' marks on the same evidence item, over the items that had at least one other mark; with no such item it is 0.

## 8. HTTP API

JSON over `node:http`. Body limit 256 KiB (`413 body_too_large`); `content-type: application/json` required on every POST (`415`); malformed JSON is `400 bad_json`. There is **no rate limiting, no session, no cookie and no CORS header**: the host puts the server behind its own TLS, authentication and limits, or binds it to localhost. Node's default server timeouts apply (a client should allow about 10 seconds). Operator routes need `authorization: Bearer <operator token>` (compared in constant time; `401 unauthorized`). Attestor routes are open because the body is signed. Every error is `{ "error": code, "message": text }` (plus `reason` for `bad_signature`); the status is the engine's (400 bad input, including `bad_json`, `bad_number`, `bad_string`, `too_deep` and `too_large`, 401 signature or token, 403 not invited, 404 unknown, 409 state conflict, 413, 415, 500 `internal` with no detail).

All bodies below are exact; unknown extra members in a request body are ignored by the engine and never stored, except in template, DID and statement bodies, which have closed member sets and are refused if they carry others.

## 8a. The browser attestor flow: signing ticket, preview, removal

**Who does what.** The operator creates the assessment and invites an attestor by DID. The host gives the attestor's client a **signing ticket**. The client, which holds the attestor's private key, builds and signs the commit, sends it, later builds and signs the reveal, and sends that. Neither the ticket nor any request ever contains the key. A host that signs on an attestor's behalf has left the protocol.

**The signing ticket** (`GET /v1/assessments/:id/ticket/:attestationId`, library `engine.ticketFor(assessmentId, attestationId)`) is public data and holds no secret:

```
{ "ticketVersion": 1, "alg": "sanad-0.1",
  "assessment": "<id>", "attestationId": "<id>.a01", "attestor": "<did>", "role": "<role>", "evidence": "<id>.E1",
  "templateHash": "<64 hex>", "levels": [0,1,2,3,4,5], "levelMap": { "<native>": level, ... },       // levelMap only if the template has one
  "commitBy": "<iso>", "revealBy": "<iso>", "state": "open|finalized", "revealOpen": false,
  "serverTime": "<iso>", "serverDay": "YYYY-MM-DD",
  "rules": { "nonce": { "pattern": "...", "minLength": 22, "hint": "..." },
             "date": { "format": "YYYY-MM-DD", "notBefore": "<evidence date>", "notAfter": "the provider day at the moment of the reveal" },
             "level": "integer listed in levels" },
  "commit": { "typ": "sanad-commit+jws", "type": "sanad-commit", "members": [...], "commit": "sha256(canonical({attestor, evidence, level, nonce}))", "post": "/v1/assessments/<id>/commit" },
  "attestation": { "typ": "sanad-attestation+jws", "members": [...], "id": "<attestationId>", "post": "/v1/assessments/<id>/reveal" } }
```

The client turns the ticket into the two requests:

1. Choose a level from `levels` (or a native mark, below) and a fresh nonce: 16 random bytes as base64url (22 characters), at least 22 and at most 128 characters of `[A-Za-z0-9_-]`.
2. `commit = SHA-256(canonical({ attestor, evidence, level, nonce }))` as lowercase hex. Payload `{ type: "sanad-commit", assessment, attestationId, attestor, evidence, role, commit, templateHash }`; `jws` is the detached JWS of section 3 with `typ` `sanad-commit+jws`. Request body `{ attestationId, payload, jws }`. Keep `{ attestationId, level, nonce }` on the device.
3. When the reveal phase is open (`revealOpen` in a fresh ticket or the public view): statement `{ id: attestationId, attestor, evidence, level, role, conflictDeclared, date, commit, nonce }`, `jws` with `typ` `sanad-attestation+jws`. Request body `{ attestationId, statement, jws }`. `date` must not be before the evidence date and must not be after the provider's current day: take `serverDay` from a ticket or `/v1/info` fetched at the time of the reveal, not the device's own clock, to avoid `bad_date` across a day boundary or a skewed clock.

**Browser helper contract.** A client needs only WebCrypto Ed25519, SHA-256, base64url and the canonical JSON of section 3, with no dependency and no network of its own. `engine/static/sanad-client.js` is the model and exports `newAttestor()` (a key pair made in the page; `{ did, kid, sign(typ, payload) }`), `prepareCommit({ attestor, ticket | assessment, attestationId?, level | native, levelMap?, nonce? })` returning `{ request, secret }`, `prepareReveal({ attestor, ticket | assessment, attestationId?, secret, date, conflictDeclared? })` returning the reveal body, and `canonical`, `sha256Hex`, `newNonce`. The Node helpers of `attestor.mjs` have the same shapes. A host may reimplement the contract in another language; the engine vectors and `test/client.test.mjs` show the exact bytes expected. A host page must keep the key in memory or in the platform's own key store, never post it, and show the attestor what is being signed.

**`levelMap` (decision, item 17 of section 14).** `levelMap` is an optional template member mapping a host-native mark label (1 to 16 letters or digits, for example `g1` to `g6`) to a Sanad level 0 to 5. It is a convention that keeps the host's scale and Sanad's level from drifting apart, and it is not applied to any stored mark by the engine. If the host wants the native mark preserved, the attestor writes it into the nonce as `nm-<native>-<random>` (random part at least 16 characters): the nonce is hashed into the commit and revealed only at the reveal, so **the blind commit is unchanged** and the native mark becomes part of the attestation (and so of the bundle hash and the credential). At the reveal, if the template has a `levelMap` and the nonce carries a native mark, the engine requires it to be listed (`native_unknown`) and to map to the revealed level (`native_mismatch`). A nonce without the `nm-` form is accepted as before; a template without a `levelMap` leaves the nonce uninterpreted. The helpers `levelFromNative`, `nonceWithNative` and `nativeOfNonce` (engine) and the `native` option of `prepareCommit` (engine and browser helper) implement this. Native marks are never sent in the clear before the reveal, and the engine never maps a mark on its own. Removing `levelMap` instead would have left every host to invent its own convention, with the risk that a native mark is sent beside the commit and so weakens blindness.

**Recognition preview** (`POST /v1/assessments/:id/preview`, library `engine.previewRecognition(id, { policy? })`) is a read-only computation that changes nothing and is not a credential. It runs the recognition function over the attestations **revealed so far** only; a commit holds no readable mark, and unrevealed marks are neither read nor counted: only the number still pending is returned. It uses the verifier's `policy` if given (`policySource: "verifier-supplied"`) and otherwise the template's recommendation (`"template-recommendation"`). The result is `{ preview: true, provisional: true, state, policySource, counts: { invited, committed, revealed, pending, notCommitted }, recognition, note }` and is always labelled provisional. It can differ from the final result as soon as another attestor reveals. Revealed marks are public once the reveal phase opens, so the preview discloses nothing that the public view does not already show.

**Invitation removal** (`POST /v1/assessments/:id/invitations/:att/remove`, library `engine.removeInvitation(id, attestationId, { reason? })`, operator only). Allowed only while the assessment is open and only before that attestor's first commit (`409 already_committed` after; `409 state` after finalize; `404 not_invited` if unknown or already removed). It deletes the invitation, keeps a record under `removed` in the public view, appends `{ type: "invitation-removed", assessment, attestationId, attestor, at, reason? }` to the `events` stream, and never reuses the attestation id (the next invitation takes the next number, so a ticket or a signature made for a removed id cannot be replayed against a new invitee). If everyone who remains has committed, the reveal phase opens at once. When the assessment is finalized the credential's `sanad.process` gains `removed: [attestation ids]`, present only if something was removed; a verifier sees it, and a credential without removals has the six members it always had. Removal is an operator power over who sits, not over any mark, and it is visible. Verifiers decide what a visible removal means for them.

**Provider time.** `/v1/info` and `engine.info()` carry `time` and `today`; tickets carry `serverTime` and `serverDay`. Deadlines, key validity on `date` and the "not after the reveal day" rule all use the provider's clock.

## 11. Security considerations, and what is not claimed

- **Replay**: every signed payload names the assessment, the attestation id and its `typ`; commits are accepted once; HTTP has no session to replay. **Malleability**: closed member sets, canonical JSON, bundle hash over complete objects, `kind`/`date` mirrored into the hashed body. **Canonical form**: one implementation (core) is used by every module; numbers are serialized in the ECMAScript form required by RFC 8785 (integers in statements; fractions only in statistics and policy fields). **Key misuse**: `kid` must belong to the expected signer and be valid on the date; issuer and log keys are separate from each other. **Timing**: secrets compared in constant time (operator token); commits are public values.
- **Backdating with a stolen key is not detected.** A key that was revoked, or stolen, can still sign statements that carry an earlier `date`; the verifier checks the key against the statement's own date, which the key holder chooses. The log timestamps come from the operator's monotonic clock and are signed by the operator, not by the attestor, and the credential's embedded entries do not tie an attestation to a commit time the verifier can check, so the log does not close this gap. The verification report does not claim to detect it (its notice says so). Mitigations lie outside the engine: short key lifetimes, revoking promptly, and keeping the signed commit statements and checkpoints.
- **Retroactive DID updates**: the holder of a valid key can sign an update whose `validFrom` lies in the past and so change which keys count for past dates. Verifiers should compare against DID histories and log checkpoints they kept earlier. The engine refuses `validFrom` earlier than the previous version's, not equal to it.
- **Checkpoints must be kept**: the log's entry chain is unkeyed; anyone who can write the store can rewrite the whole log. Rewriting is detected only by a consistency proof against a checkpoint that someone kept. Verifiers must also check the checkpoint's `logId` against the log they expect.
- **What the commit does not cover**: `date` and `conflictDeclared` are covered by the attestor's signature but not by the commit, so an attestor can choose them after seeing the other commits and, once the first reveal is public, after seeing marks (for example declare a conflict to withdraw one's own mark). Adding `conflictDeclared` to the commit preimage passes the 20 core vectors (they are sealed at run time) but would change the commit of every credential issued under `sanad-0.1`; it is recorded as a specification decision (`docs/SPEC-DECISIONS-NEEDED.md`, decision 3), not changed here. Small-order Ed25519 public keys are refused everywhere.
- **Commit-before-reveal is operator-attested.** The credential carries the attestations but not the signed commit statements; the log has a leaf for each commit, but a verifier cannot reconstruct the commit statements from the credential and so cannot prove, from the credential alone, that every commit was made before any reveal. An operator who controls the clock can order events as it likes. The protection is outside the credential: examiners' signed commits kept by others, and checkpoints that people keep. The engine therefore makes the order monotonic on its side (the clock never runs backwards, a commit is refused once any reveal exists) but does not claim to prove it to a third party. See `docs/SPEC-DECISIONS-NEEDED.md`, decision 1.
- **did:web is operator-asserted.** The engine registers a `did:web` key history as given by the operator (trust on first registration) and does not prove control of the domain. A verifier must pin the keys; a credential's embedded history is never trusted by default.
- **Statistics are issuer-supplied** (section 7).
- The engine has had **no external cryptographic review** and **no independent implementation** checks its outputs; the Ed25519 and SHA-256 primitives are Node's. Collusion, help off camera and identity checks are outside what any software can prove (spec section 12).

## 12. Integrating an exam service (the adapter)

A host service keeps its own workflow (bookings, payments, rooms) and calls the library: `createEngine({ store, issuer: { did, kid, sign }, log, resolver, clock })`, then `registerTemplate`, `createAssessment`, `invite`, `commit`, `reveal`, `finalize`, `verifyCredential`, `stats`. It may share its SQLite database through the `sqlite` adapter with a table prefix. For portability the host **vendors** `engine/dist/sanad-engine.mjs` (one file, no dependencies) and records its SHA-256 and the source commit; a test in the host checks the hash. A path dependency on a local checkout is not portable and is not used.

An example host, to show how a platform maps its own concepts (the engine does not know this host and gives it no special status; any platform is one host among many): an examiner's device key is the attestor key (`did:key` of the raw public key); the browser signs the commit and the attestation; a committee's sitting is one `sitting` evidence item; the credential is issued when the host's registrar releases the result and is handed to the candidate by the host. If the host grades 1 to 6 while Sanad levels run 0 to 5, the mapping belongs to the host and to the template's optional `levelMap`; the host may bind its native mark into the nonce (for example `h1-<native level>-<random>`, within the nonce alphabet `[A-Za-z0-9_-]`) so that the two cannot drift apart. Choosing the mapping is the host's decision. `docs/TUTORIAL-plug-sanad-into-any-system.md` walks through three modes (vendored library, sidecar HTTP service, verify-only) with a runnable toy host.

## 14. Open points (spec text versus the reference code; the spec is not edited)

1. **Commit form.** Spec 3.4: "sha256 of level|nonce". Reference and vectors: `SHA-256(canonical({attestor, evidence, level, nonce}))`. The engine follows the vectors (the binding to attestor and evidence also stops copying another attestor's commit).
2. **Field names.** Spec 3.4 names `evidenceId`, `reveal`, `sig`; reference uses `evidence`, `nonce`, `signature`, and adds `prev`. Spec 3.3 evidence fields (`claimId`, `takenOn`) differ from the reference (`date`, `summary`, `body`). The engine follows the reference.
3. **Evidence hash coverage.** Spec 4.2: the hash covers the object without `hash` and `sig`. Reference: the hash covers `body` only, so `kind` and `date` are outside it. The engine mirrors them into the body and covers them by the bundle hash.
4. **Month length.** Spec 5: 30.436875 days. Reference: 30.4375. The difference is below the 0.001 tolerance for the vectors but is a defect in one of the two texts.
5. **What a signature covers.** Spec 3.4: a JWS "over the canonical attestation". With the `prev` chain the attestor cannot know `prev` when signing; the engine signs the attestation without `prev`, `hash` and `signature`.
6. **Signature failure in R1.** R1 lists hash, commit-reveal and chain failures; it does not list a failed signature. The engine passes a signature check to the core, which then drops the attestation under R1 with the reason "signature". Without the check the core behaves exactly as in v0.1.
7. **`bundleHash`.** Spec 4.4 calls it the root hash of the claim-evidence-attestation tree without defining the tree; the engine's definition is in section 3.
8. **Agreement statistic.** "Median of the other attestors" does not say which median for an even count, nor what agreement is with no co-attestor; the engine uses the lower median and 0. Spec 3.4 says "on the same sittings"; the engine counts every evidence item with at least two marks (sittings, artifacts, peer reviews). Which is meant needs a decision.
9. **Credential proof.** Spec 6 does not say how the credential is secured; the engine uses a detached JWS. A W3C Data Integrity suite (`eddsa-jcs-2022`) would be the standard choice and is a candidate for a later version.
10. **Log leaves.** Spec 8 logs attestation hashes; the engine also logs commits, missing reveals and bundle hashes, so that the order "all commits before any reveal" can be shown.
11. **No `assessment.mjs`.** Section 2 of the first draft planned a separate state-machine module. The state machine is about 130 lines and shares the store, the log and the resolver with the rest of `engine.mjs`; splitting it would only have passed those through arguments. The functions that must run on the attestor's side (`attestor.mjs`) are separate, so that a client bundle never contains the operator code. No behaviour differs from section 4.
12. **Subject form.** Section 4 said the subject is pseudonymous. The engine enforces a strict form so that a name or an e-mail address cannot be typed in by mistake; the current rule is item 30. A strictly formed value can still be derived from personal data: the form check is a guard rail, not proof of pseudonymity.
13. **Verify route pins the operator's issuer by default.** `POST /v1/verify` and `engine.verifyCredential` (the engine's method) pin the engine's own issuer, log key, log id and template unless the caller supplies `trustedIssuers`, `trustedLogKeys` or `trustedLogIds`. The standalone `verifyCredential` and `sanad-engine verify` pin nothing by themselves: without `trustedIssuers` and `trustedLogKeys` they fail (`ok: false`) unless the caller passes `allowUnpinned`, in which case the report warns "not pinned" (item 23). A verifier of credentials from other issuers must name the issuers and log keys it chooses to trust.
14. **Bundle hash record.** `engine/build.mjs` writes `dist/sanad-engine.mjs.sha256`; a test compares the committed bundle with a fresh build and the record with the file. The bundle includes the HTTP server and the demonstration helper (`demo`); the CLI is not in the bundle.
15. **Engine vectors are regression vectors.** They are generated by `vectors/generate.mjs` from this implementation and reviewed by hand; they are not an independent check, because no second implementation exists. They pin bundle hashes, log roots and refusal codes, so that a change in behaviour is visible.
16. **CLI scope.** Operator commands act on a data directory (single process: not while `serve` runs on the same directory). Attestor commands (`commit`, `reveal`) keep the level and nonce in `<keyfile>.secrets.json` (mode 0600) next to the attestor's key; with `--url` they talk to a running server and send only signed statements.
17. **`levelMap` is kept and given a meaning** (details in section 8a): host-native label to level, carried hidden in the nonce as `nm-<native>-<random>`, checked at the reveal, never applied to a stored mark. Template keys are now restricted to 1 to 16 letters or digits (a template whose `levelMap` has other keys, such as `native-1`, is refused; no earlier release published such templates).
18. **Provider time** is part of `info()` and the ticket.
19. **Recognition preview** exists, over revealed attestations only, always marked provisional, under the verifier's policy or the template's labelled recommendation.
20. **Invitation removal** exists before the first commit, with a never-reused attestation id, an `events` record and an optional `process.removed` member in the credential. The credential shape check accepts the process object with or without `removed`, so credentials issued earlier still verify. The log has no leaf kind for removals (the log format is unchanged).
21. **Public method name `ticketFor`** (not `signingTicket`): the principle test refuses any engine method whose name contains `key`, `sign` or `secret`, so that no method can suggest that the engine signs or holds secrets.
22. **HTTP bodies are now documented in full** in section 8, including the rate-limit statement (none), the body limit and the timeouts.
23. **Review round: pins.** A DID string is a name, not a key. `verifyCredential` takes keys from the verifier's resolver, then from `trustedDidHistories`, and only then from histories embedded in the credential; an embedded history makes `ok` false unless `pinnedKeys` names the key that verified (or the insecure `allowEmbeddedDids` is set). An unpinned issuer or log key makes `ok` false unless `allowUnpinned`. `trustedLogIds` pins the log id.
24. **Review round: verifier owns policy and day.** The seven policy fields and `asOf` are all required everywhere (core `recognise`, `infer`, engine preview, HTTP). `verifyCredential` has no default policy or day: `useRecommendedPolicy` (labelled in `basis`) or `useVerifierClock` are explicit. The CLI refuses to verify without `--policy`, unless `--use-recommended-policy` is given, which prints that the issuer's recommendation was used.
25. **Review round: statistics, allow-list, duplicates, ids, roles.** `attestorStats` and `allowedAttestors` are verifier options; the core drops a second mark by the same attestor on one evidence item (R1); ids must carry the assessment prefix; a supplied template is checked for hash, roles and evidence kinds.
26. **Review round: phases.** The engine clock never runs backwards (and each assessment keeps a high-water mark); a commit is refused once any reveal exists; `late` is recorded only for a validly signed statement of the invited attestor.
27. **Review round: finalize** enforces the template minimum (`below_template_minimum`, override `allowShortfall` recorded as `process.shortfall`), is idempotent after a crash, and an `auto` evidence item needs `body.autoLevel`.
28. **Review rounds: limits (normative for verification).** `verifyCredential` and `/v1/verify` refuse a document with more than 200 attestations, 200 evidence items, 2000 log entries or 100 DID histories, a DID history with more than 16 versions, or a version with more than 8 keys or 16 revocations (`shape` check, `too_large` over HTTP); registration enforces the same history limits. Work per verification is then bounded by these numbers: only the key named by a signature's `kid` is decoded (no work for the other keys of a version), each attestor signature is verified once and the result is shared, DID histories are not copied per call, and verification stops at a failed issuer proof unless `diagnose` is set. A test pins the worst case (16 versions of 8 keys, 200 forged attestations) at well under 100 ms. These are bounds on work, not rate limiting; the server has none.
29. **Review round: input hygiene.** The HTTP body is scanned for nesting depth beyond 64, integers beyond 2^53 and non-finite numbers before parsing, and checked for lone surrogates after; each refusal is a 400 with a code. After a 413 the connection is closed and at most 1 MiB more is read. Internal errors are logged without stack traces.
30. **Review rounds: subject form.** The subject must be `urn:uuid:<RFC 4122 UUID in lower case>` or `urn:sanad:subject:<32 to 64 lower-case hex characters>`; everything else, including other URN namespaces, is refused (`bad_subject`). This is a guard rail against typing a name by mistake, not proof of pseudonymity: the host must generate the value without using personal data. Evidence `summary` and `body` and the assessment id are free text that ends up in the public credential: they must not hold personal data either. The dead `subject_as_attestor` check (a DID can never equal a URN) is replaced by an optional `subjectDid` on the assessment, which cannot be invited as attestor.
31. **Review round: not changed, decided elsewhere.** Carrying commit statements in the bundle, what the attestor signature covers, `conflictDeclared` in the commit, statistics made verifiable, the credential proof format and the other items of `docs/SPEC-DECISIONS-NEEDED.md` are left unchanged.

32. **Differences from the v0.1 reference (open spec decisions).** The core differs from the code published with SANAD-SPEC-0.1 in these ways: (1) a second mark by the same attestor on one evidence item is dropped under R1 (v0.1 counted both); (2) with the optional signature check, a failing signature drops the attestation under R1 (v0.1 did not check signatures); (3) a policy must be complete and in range and `claimedLevel` must be 0 to 5, otherwise the function throws a `RangeError` (v0.1 computed from whatever it was given); (4) the attestor name `replay` is reserved, statistics are read from own numeric properties, an optional allow-list exists. On credentials without duplicate marks, with a valid complete policy and without a signature check the results equal v0.1's; the 20 vectors give the same results. A review measured different results on 2,500 of 20,000 random credentials that contained duplicate marks. The algorithm string stays `sanad-0.1`; `docs/SPEC-DECISIONS-NEEDED.md` decision 11 asks whether to name the changed rules `sanad-0.2`.
33. **Month length boundary.** The core uses 30.4375 days per month; the specification text says 30.436875. The difference is not below tolerance at a hard threshold: evidence of 1461 days with a half-life of 12 months is exactly four half-lives under 30.4375 and is kept, but is 48.0003 months under 30.436875 and would be dropped (R2). A test pins the core's behaviour at this boundary; the constant is not changed here (decision 10).
34. **Chain rule.** The specification text says that when a link fails, that attestation "and therefore also its honest successor" is dropped; the core drops only the attestation whose own `prev` does not match. A reviewer's example gives recognised level 3 with confidence 0.783 under the core rule and provisional with confidence 0.464 under the literal text. Behaviour is unchanged and a test pins it (decision 12).
35. **Roster lock (second review, M10).** The reveal phase opens only when every evidence item that needs human attestors has `attestors.min` invitations (or the operator called `closeInvitations`) and everyone invited has committed, or at `commitBy`. A single early invitee therefore cannot open the phase alone.
36. **Verifier checks added (second review, M5).** With a template the verifier also checks the template's evidence items for completeness, the attestor minimum per evidence item (conflicted attestors do not count) and live sitting, and treats a shortfall without a recorded `process.shortfall` as a failure. Without a template the `process` record is still checked against the bundle (counts, missing, late). A report whose checks failed labels its recognition `unverified`.
37. **`pinnedKeys` pins a key, not its revocation history (M11).** A verifier that pins a `did:web` key by `pinnedKeys` accepts that key whenever the credential's embedded history lists it as valid on the statement's date; it does not learn of a revocation unless it holds the history. The remedy is `trustedDidHistories`: the verifier keeps the DID histories it trusts and passes them in; revocations in them then apply.
38. **Clock high-water mark.** The engine's clock never runs backwards, which means a reading that jumps far forward cannot be undone: every deadline of an assessment touched afterwards has passed. The operator keeps the clock right; the engine does not guess which reading is wrong. Log timestamps come from the same monotonic clock and also survive restarts (the last log entry's time seeds it).
39. **Commit and finalize are retry-safe.** A commit's log leaf is appended once (a retry after a crash between the append and the save finds it); finalize likewise (item 27).
40. **Evidence keys** that look like attestation ids (`a01`, `a02`, ...) are refused in templates, so evidence ids and attestation ids cannot collide.

41. **Cross-checkers (Python and Ruby).** They verify with their own Ed25519, canonical JSON, RFC 9162 and recognition code. They require the issuer and log key to be pinned (`--issuer`, `--log-key`) or an explicit `--allow-unpinned` (internal consistency only), because any engine's credential is internally consistent; they handle a credential whose embedded log entries are a subset of a larger log (every credential after the first on a shared log); and a malformed input ends in a failed check, not a crash. The confidence they print equals the engine's when the same policy and evaluation day are used (tests compare them at three days); a gap seen once (0.933 against 0.936) came from the Ruby verifier's defaults being used (2026-03-12 and half-life 24 months), not from rounding or month length.

## 15. Notes for a second implementer

A second implementation (the Python cross-check in `engine/test/crosscheck/` is one) needs these points, which the first draft of this document left implicit:

- **Commit leaf `ref`.** The log leaf of kind `commit` has `ref = SHA-256(canonical(commit statement))` where the commit statement is `{ type: "sanad-commit", assessment, attestationId, attestor, evidence, role, commit, templateHash }` (the payload the attestor signed), not the `commit` hash itself. Leaves of kind `attestation` carry the attestation `hash`; `bundle` the `bundleHash`; `missing-reveal` the `commit` hash of the attestor who did not reveal.
- **Order of ids.** `evidence` and `attestations` are sorted by `id` in UTF-16 code unit order (JavaScript string comparison) before hashing and chaining; canonical JSON sorts object keys the same way. Ids built from ASCII agree with byte order; others may not.
- **Attestation hash coverage.** `attestation.hash = SHA-256(canonical(attestation without hash and signature))`: all of `id, attestor, evidence, level, role, conflictDeclared, date, commit, nonce, prev`. The attestor's signature covers the same members **without `prev`** (the attestor cannot know `prev` when signing). The chain link `prev` is the previous attestation's `hash`, `GENESIS` for the first.
- **Ed25519.** Verify strictly (RFC 8032): reject a signature whose scalar `S` is not below the group order, reject non-canonical point encodings, and reject public keys of small order (the identity and the other torsion points) everywhere, including `did:key`. Node's `crypto.verify` is the reference here; implementations that accept `S >= L` or small-order keys produce different results on adversarial input.
- **JWS.** Detached compact JWS with a canonical-JSON header `{"alg","kid","typ"}` in that member set only; the signing input is `BASE64URL(header) + "." + BASE64URL(canonical(payload))`; unpadded base64url, and the decoder rejects non-canonical encodings.
- **`logKey` and `logId`.** `sanad.log.logKey` is the DID that signed the checkpoint (`sanad-checkpoint+jws`); a verifier pins that DID's key (not the string). `sanad.log.logId` is a name chosen by the operator that appears inside the signed checkpoint payload; it names one log, and pinning it (`trustedLogIds`) stops a checkpoint of another log of the same operator from being presented. The embedded entries and inclusion proofs are against the checkpoint of `checkpoint.payload.size` leaves; the credential does not prove consistency with any earlier checkpoint.
- **Numbers.** Canonical JSON uses ECMAScript `Number` formatting (see section 3).
- **Credential id and time.** The id is `urn:uuid:` derived from the assessment id and the bundle hash; `proof.created` equals `validFrom`.

## 16. Public chain additions (engine 0.3, unreleased)

Normative text: `spec/SPEC-v0.2.md` (draft). Only hashes, signed checkpoints and credential bundles are public, as plain static files that anyone can mirror; no video is ever part of the chain.

- **Sitting evidence** (`src/evidence.mjs`): `sittingId`, `paperFingerprint`, `strokeLogHead`, `recordingSha256`, `recordingCipherSha256`, `recordingBytes`, `identityAssurance` (A0 to A2, signed by the checker, `sanad-identity+jws`) and `publication` live in the hashed evidence body. Template flags `requireRecordingHash`, `requireStrokeLogHead`, `requireIdentityAssurance` make members mandatory (finalize refuses, or records `process.shortfall`). The verifier check `sitting-evidence` validates the shape and the identity signature; option `minIdentityLevel`.
- **`addEvidence(assessmentId, { key, body })`** (HTTP `PUT /v1/assessments/:id/evidence/:key` with `{ body }`): adds absent members before the first commit; never overwrites (`evidence_conflict`); refused after any commit (`evidence_sealed`); recorded in the events stream and in `process.evidenceAdded`. Not done: binding each commit to the evidence hash it saw (it would change the commit statement; the engine instead freezes the evidence at the first commit).
- **Static export** (`src/export.mjs`): `export <credential-id> --out <dir>` writes `issuer.json` and `bundles/<bundleHash>/` (credential, split files, consistency proofs, DIDs, optional witnesses and status snapshot, manifest, README); `verify-bundle <dir>` checks it with no server. `urn:sanad:bundle:<hash>` resolves to `<base>/bundles/<hash>/`.
- **Checkpoints and witnesses** (`src/witness.mjs`): `publish-checkpoint --out <dir> [--daily]`; `witness --log <url|dir> --out <dir> --key <file> --log-key <did>` (fetch, check consistency with the stored checkpoint, cosign, alert on fork or rollback, exit 3); `verify-bundle --witness <did> --require-witnesses N`. A scheduled job in a public git repository is the intended runner. The witness job supports `did:key` log keys only.
- **Revocation** (`src/statuslist.mjs`): config `statusUrl` makes finalize add `credentialStatus` (W3C Bitstring Status List entry); `revoke`, `status publish`; verifier options `statusLists`, `requireStatus`, `now`. Positions are sequential (a random position would hide issue order; decide before production).
- **Verifiers**: single-file browser page `verifiers/browser/sanad-verifier.html` (build: `node engine/verifiers/browser/build.mjs`); independent Python verifier written from the spec text only in `verifiers/python/`; fixtures in `verifiers/fixtures/` (`node engine/verifiers/make-fixtures.mjs`).
